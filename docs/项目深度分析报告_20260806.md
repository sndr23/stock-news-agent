## 二、新发现的问题（本轮重点）

### P1-1 实时推送 LLM 判定无总超时熔断（真实生产风险）

**定位**：`scripts/real_time_push.py:861`（`_llm_judge` 内）

```python
raw = _call_llm_api(_LLM_SYSTEM_PROMPT, _build_llm_user_prompt(batch), timeout=90, max_retries=1)
#                                                                        ↑ 未传 deadline！
```

**根因**：`nodes.py` 的 `_llm_analyze_batch_structured` 全程传递 `deadline`（300s 总熔断），而实时推送的 `_llm_judge` 调用 `_call_llm_api` 时**遗漏了 deadline 参数**（其默认值 0=不限）。候选上限 40 / 批 8 = 5 批，单批最坏 90s×2 次尝试 = 180s，5 批理论最坏 **900s = 15 分钟**，而 GitHub Actions 配置 `timeout-minutes: 10`。

**影响**：
- LLM 慢时（Agnes 实测单次 30~65s，5 批约 150~325s，尚在窗口内）风险窗口出现在：LLM 降级重试叠加 + 抓取 120s 时，总时长逼近 10 分钟上限；
- 任务被 Actions 强杀 → 已推送但状态未保存 → **下轮重复推送**；未推送的直接丢失。

**建议**：给 `_llm_judge` 传入 `deadline=time.monotonic()+300`（与批处理管线对齐），并在批次循环入口检查熔断。

### P1-2 候选溢出被永久标记 seen → 重大消息漏推（比重复推送更严重）

**定位**：`scripts/real_time_push.py:1145-1150` + `1298-1302`

```python
if len(candidates) > max_candidates:
    candidates.sort(key=lambda x: x["_pref_score"], reverse=True)
    overflow = candidates[max_candidates:]
    candidates = candidates[:max_candidates]
    # overflow 不推、不进 LLM 判定
```

随后 5c 末尾：`for n in new_items: if n["_fp"] not in cand_fps ...: seen[...]=pushed:False` → **溢出条目被写入 seen 且 pushed=False，48h 窗口内不再尝试**。

**影响**：突发行情下真正重要的第 41+ 条候选被永久放弃（不是延迟重试），**漏推**。上轮报告认为"不记指纹导致重复消耗"，实际代码行为是"记指纹导致永久放弃"，性质更严重。

**建议**：溢出条目**不落 seen**（保持未处理状态，下轮重新评估），或改为"溢出条目降级挂起下轮重试"。

### P1-3 复盘报告宏观数据硬编码且已过期一个月

**定位**：`daily-review/build_report.py:88-95`

```python
macro = {
    "usdcny": "6.7484", "usdcny_chg": "0.02", "usdcny_ytd": "-3.41",
    "us10y": "4.519", "us10y_date": "2026-06-30",   # ← 6月30日数据，报告却是8月5日
    ...
}
```

**根因**：宏观数据字典写死在代码里，注释标注"neodata 文本摘要结构化提取"但实际未接入 `neodata_macro.txt` 采集数据。报告日期 2026-08-05，展示的美债收益率日期却是 2026-06-30。

**影响**：复盘报告展示**过期一个月的汇率/美债/油价数据**，误导决策。同类风险：`daily-review` 目录未被 `.gitignore` 排除，生成的 HTML 若入库会导致报告陈旧残留。

**建议**：从 `_data/neodata_macro.txt`（已采集到原始数据）解析注入；或至少标注数据时间戳；将 `daily-review/` 加入 `.gitignore`（生成的 HTML/数据不入库）。

### P1-4 ~~关键词匹配逻辑两管线不一致~~ → 修正为 P2：英文缩写词边界保护缺位（两管线共有）

**定位**：
- `src/tools/calculators.py:161-175`：`_TECH_ENGLISH_WORDS` 仅含 13 个科技缩写（CPO/PCB/HDI/FPC/EDA/GPU/CPU/HBM/DDR5/CoWoS/TSV/ASML/AMD），有词边界正则
- `src/tools/keyword_tables.py:23-50`：`HIGH_SIGNAL_KEYWORDS` 中英文词为 `ST/*ST/IPO`，**均不在 `_TECH_ENGLISH_WORDS` 中**
- `src/agent/nodes.py:1288-1295`：`_signal_kw_pattern` 对非 `_TECH_ENGLISH_WORDS` 词返回 `re.escape(kw)`（裸子串）→ nodes 对 `ST` 也是裸子串匹配
- `scripts/real_time_push.py:676/234`：`kw in text` 裸子串匹配

**复核结论（2026-08-06 二轮实证）**：首轮判断"批处理用词边界、实时用裸子串，两管线不一致"**不成立**——`ST/*ST/IPO` 在两管线中均为裸子串匹配，行为一致。真实问题是：**`HIGH_SIGNAL_KEYWORDS` 的英文缩写（ST/IPO）全项目无词边界保护**（两管线共有缺陷），`_news_fingerprint` 中 "STMicroelectronics" 等可误命中 `ST` → 指纹退化为 `sig:['ST']` → 与其他含 ST 的新闻共享指纹 → 漏推。降级为 **P2**。

**建议**：将 `ST` 加入词边界保护（与 AMD 同策略），或在 `HIGH_SIGNAL_KEYWORDS` 中把 `ST` 拆为 `ST股/*ST` 复合词并加边界。实测 `'STMicroelectronics 财报' -> hit=True`（应 False），`'ST华微 公告' -> hit=True`（应 True）。

## 六、结论

项目围绕"重大资讯不漏推、日常不打扰"目标，工程质量**高于同类项目平均水平**：多层去重、LLM idx 对齐、Gist 读改写合并、挂起重试机制均经过实证打磨，291 项测试全绿。

**本轮新增的核心风险点**：① 实时推送 LLM 判定无总超时熔断（可能被 Actions 强杀致重复推送）；② 候选溢出被永久 seen（真正重要的第 41+ 条会被漏推）；③ 复盘报告宏观数据硬编码且过期一个月。三者均为**数据正确性/推送可靠性**问题，建议优先于历史遗留的"死代码瘦身"处理。

**最值得投入的方向**：先修 P1-1~P1-2 两个正确性问题（半天工作量），再做架构瘦身（P0），最后补 CI 测试门禁与运维告警（P2）。
