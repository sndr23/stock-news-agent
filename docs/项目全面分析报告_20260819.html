01项目定位与核心目标

一句话：做「A股版财联社」——只推改变市场逻辑的重大事件，不推流水。

产品形态：8 个新闻源 + 2 个交易所信号源并行抓取 → 三层近似去重 → 事件级指纹增量检测（48h）→ 规则预筛 → LLM 严格判定 → 强档门槛（仅 bullish / bearish）→ 同事件合并 → 跨轮同事件拦截 → PushPlus / 企业微信推送（红涨绿跌）。

用户口径（2026-08-03 起固化）：预筛通过的全部候选必须由 LLM 判定推/不推，Python 规则不得直接通关；仅强利好 / 强利空推送；只影响中小市值个股自身的消息不推。

2026-08-14 重大转向：用户反馈「推了很多利好但 get 不到万亿级量化资金的点」（8-13 日本加息引发 A 股跳水，系统全天 0 推送日元/套息资讯）。由此确立双管线架构：资讯事件流 + 量化因子流（技术面 / 宏观流动性 / 资金流），并引入 risk_off 风险收缩期联动与「市场环境」融合展示。

05核心设计决策与工程质量

本项目最突出的工程特征是「实证驱动 + 防御式编程」，每个规则都有真实事故/审核案例背书。

5.1 三层去重体系

层级机制解决的问题
入口近似去重URL 规范化 → 标题精确 → 32-bit SimHash 海明距离 ≤3多源同一事件措辞不同，先收敛再进指纹，省 LLM token
事件级指纹（跨轮）个股+事件组+核心金额 / 信号词 / 标题主语前 6 字，48h 窗口同事件多源报道共享同一指纹，48h 内只处理/推一次
推送级事件签名（同轮+跨轮）LCS 连续子串 + LCS 子序列 + Jaccard + 实体模糊重叠 + 事件短语锚 + 方向守卫（7+ 分支）指纹分裂的同事件（金额表述/信号词子集差异）只推最优一条

5.2 LLM 严格判定（无规则直推）

  • idx 精确对齐：给每条候选注入 _judge_idx，LLM 回显 idx 后按索引合并——标题匹配仅作兜底（实证：60 条仅 26 条标题精确命中，是漏推主要根因）。
  • 挂起而非否决：LLM 未回显/批次异常 → judged=False 挂起，不推、不落指纹，下轮重新判定——防漏推。
  • 总超时熔断：单轮 LLM 判定 300s 上限，批次入口+批次完成双重检查，防止突破 Actions 10min 上限。
  • JSON 容错五连：代码块剥离 → 括号平衡扫描 → _repair_json（中英标点/裸换行）→ 逐对象解析 → _rescue_judge_object 正则抢救。

5.3 状态持久化与并发安全

  • 云端 Gist（real_time_state.json + factor_state.json 并列）读-改-写合并，本地与云端并发不互相覆盖。
  • P0 事故教训（2026-08-13）：seen 无上限膨胀至 0.72MB → Gist 写入截断 → 状态被覆盖清空。修复：SEEN_MAX=3000 上限 + 读取/合并失败 fail-stop（CI 下宁可报错不可丢去重基准）。
  • Gist CDN 缓存问题：URL 追加时间戳参数绕过缓存，写后立即读会命中旧快照。

5.4 防御式编程惯例

LLM 输出不可信已成体系化防御：_as_list（防 set() 拆字）、_as_bool（防 "push":"false" 字符串真值误判）、_to_float、_env_int（防非法 env 导致 import 即崩）、_normalize_direction（6 档方向别名收敛 + 规则兜底）、_normalize_entity（别名/代码后缀归一化）。

10风险评估与改进建议

按风险等级排序，均为基于代码审读与运行日志的客观判断。
1. 单文件巨型化与规则复杂度膨胀（高）
real_time_push.py 2,722 行、_is_same_event 有 10+ 启发式分支，每个分支都是一次「实证补丁」。收益是精确，代价是（a）可维护性持续下降；（b）分支间交互难以穷举（如 _MARKET_STATE_EVENTS 过滤就影响 4 个分支）。建议：将去重/合并逻辑抽为独立模块并补充分支组合测试；中长期可评估用 embedding 语义聚类替代部分 LCS/Jaccard 规则。
2. 关键词表多套并存，仍存在漂移面（高）
已收敛到 keyword_tables.py，但 _TECH_SECTOR_WORDS（real_time_push 内嵌）与 OVERSEAS_TECH_KEYWORDS 仍各维护一份科技词，文档亦承认存在差异（如「液冷/散热/数据中心」缺失实证）。建议：统一并入共享词表，并为「降级判定」与「外围科技增强」两个语义分别命名，杜绝一词两义。
3. LLM 单点依赖（中高）
全部候选必须 LLM 判定，模型为 deepseek-v4-flash:free（免费档），存在速率限制与可用性风险；300s 熔断下突发大行情可能出现大比例挂起。建议：监控免费档限流情况，必要时为高信号直通类事件预留付费模型后备通道；增加 LLM 判定「未判定率」指标告警。
4. 本地与云端双端同跑的风险（中）
代码已实现读-改-写合并，但文档明确提示「双端同跑浪费 LLM 额度且偶发重复」。建议：生产环境明确单一运行端（推荐仅云端），本地 --loop 仅用于开发调试。
5. 废弃代码与依赖未清理（中）
src/agent/ 1,735 行已 DEPRECATED 仍保留，langgraph/langchain 依赖仍被引入。建议：确认无回滚需求后移除，可显著缩小依赖面与攻击面（云端每次都要 pip install）。
6. 信号回测样本不足（低-中）
signal_backtest.py 为 08-19 新增，样本 <10 不计比率。推送方向有效性需要数周数据积累才能指导阈值调优——这是「可信度闭环」的关键拼图，建议保持每日运行并定期复核一致率。
7. Actions 免费额度逼近上限（低）
私有仓库 2,000 分钟/月，当前调度约 1,500-1,900 分钟/月。若用量吃紧可下调为美股盘中 30min / 其余 60min，或考虑公开仓库。
8. 数据源反爬与变更风险（低）
东财 K 线已反爬（已切新浪+腾讯降级）；akshare 接口列名变更风险已通过版本锁定缓解。建议：为每个数据源保留独立的失败降级路径（现已具备），并纳入心跳监控。

11总体结论

从产品、工程、数据三个维度给出评价。

产品层面（成熟）：已实现「财联社式」重大消息推送体验，且经 8-13 日本加息漏推事件完成了从「单维个股利好」到「多维量化因子均衡」的架构转向，方向正确。

工程层面（扎实）：实证驱动 + 防御式编程 + 542 项测试门禁 + 多轮人工审核闭环，是本项目最大的资产。状态管理经历了 P0 事故并完成 fail-stop 加固，并发安全设计到位。

数据层面（可信）：数据源多且互为备份（新闻 8 源 / 行情双降级），免费接口为主、成本可控；信号回测（P2-3）是补齐「推送质量可量化验证」的最后一块拼图，值得持续投入。

优先级建议：短期——收敛双科技词表、明确单一运行端；中期——去重规则模块化 + 语义聚类评估、清理废弃 LangGraph 管线；长期——积累回测数据驱动阈值与 Prompt 迭代。
