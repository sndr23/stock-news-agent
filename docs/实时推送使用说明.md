# 重大资讯实时推送（多源 · 财联社式）

每 30 分钟自动抓取多源新闻并筛选，**仅将重大新闻推送到手机（微信）**，
非重大新闻静默丢弃、不打扰。
（注：原"每日 4 次汇总推送"已于 2026-07-31 移除，本项目仅保留实时推送。）

## 数据源（多源聚合，不限于财联社）

- **新闻源（6 个并行抓取 + 跨源去重）**：东财快讯、财联社电报、新浪财经、
  同花顺快讯、富途全球快讯（美股/港股/国际宏观）、华尔街见闻（地缘/外围/大宗）
- **信号源**：交易所龙虎榜机构动向、业绩预告
- 公告源暂未纳入（量大、严格模式下价值密度低）；如需可后续开启

## 架构

```
多源聚合(6新闻源+信号) ──每30分钟(云端)/120秒(本地)──> 事件级指纹去重
    ──> 规则预筛(重要度≥0.55 或 高信号词) ──> LLM严格判定(idx对齐/影响分/6档方向/范围/事件主体)
    ──> 强档门槛(仅 bullish/bearish，2026-08-04 起) ──> 同事件合并 ──> 通过阈值 ──> 48h同事件拦截
    ──> PushPlus 微信单条快讯(红涨绿跌)
    ──> 未通过 ──> 静默丢弃(仅记录指纹，不推送)
LLM 判定失败(未回显/批次异常) ──> 挂起不推、不落指纹，下轮重新送 LLM 判定
      （2026-08-03 起删除规则降级直推路径：预筛通过的全部候选必须由 LLM 判定推/不推）
状态: GitHub Gist(云端) / logs/real_time_state.json(本地) · 48h 窗口滚动清理
      Gist 写回为读-改-写合并，本地与云端并发不再互相覆盖 pushed 标记
```

> 项目内还有一套 LangGraph 批处理管线（src/agent/：抓取→预筛→LLM标签化→排序），
> 是早期的“汇总报告”分析引擎，当前无生产入口，作为共享分析库保留；
> 两条管线共用同一份关键词表（src/tools/keyword_tables.py）与工具层。

## 首次部署（7 步，约 10 分钟）

### 1. 获取 PushPlus token（推送渠道，无需企业微信）
1. 电脑访问 [pushplus.plus](https://www.pushplus.plus/) 或用微信扫码进入
2. 微信扫码登录 → 按提示完成实名认证（影响推送额度）
3. 左侧菜单 **一对一推送** → 页面显示的 token 即 `PUSHPLUS_TOKEN`（形如 `xxxxxxxxxxxxxxxx`）
4. 微信中关注"**PushPlus**"服务号——推送消息就在这里接收（体验类似公众号推文）

> 免费版 200 条/天、单条 ≤5000 字，严格模式一天 3-10 条完全够用。

### 2. 创建 Gist 用于云端状态去重
GitHub → 页面右上角 `+` → **New gist** → 随意建一个含占位文件（如 `placeholder.txt`）的
**Secret gist**（必须 secret，状态含标题文本）→ 创建后浏览器地址栏最后的 ID 即 `GIST_ID`
（形如 `abcdef123456...`，gist 所有者是哪个账号都行）。

### 3. 生成 Gist 访问 Token
GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) →
Generate new token → 勾选 `gist` 权限 → 生成并复制（只显示一次）→ 即 `GIST_TOKEN`。

### 4. 配置 GitHub Secrets
仓库 → Settings → Secrets and variables → Actions → New repository secret，新增：

| Secret 名 | 值 |
|---|---|
| `PUSHPLUS_TOKEN` | 第 1 步的 token |
| `GIST_TOKEN` | 第 3 步的 token |
| `GIST_ID` | 第 2 步的 gist ID |

（`OPENROUTER_*` 三个 secret 为 LLM 判定所需，沿用项目既有配置。）

### 5. 生成定时触发 Token（给 cron-job.org 用）
GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) →
Generate new token → **勾选 `repo`（含 actions:write）** → 生成并复制（只显示一次）。
这个 token 只填进 cron-job.org，**不要**存进 GitHub Secrets。

### 6. 配置 cron-job.org 定时任务（分时段加速，2026-08-04 起推荐）
1. 注册并登录 [cron-job.org](https://cron-job.org)（免费版即可）
2. 控制台 → **Jobs → Create cron job**，每个 Job 的公共配置：
   - **URL**（POST 到 GitHub Actions API）:
     `https://api.github.com/repos/{你的用户名}/{仓库名}/actions/workflows/realtime-push.yml/dispatches`
     （workflow 文件名可直接作为 workflow_id）
   - **Request method**: `POST`
   - **Headers**:
     - `Authorization: Bearer {第 5 步的 token}`
     - `Accept: application/vnd.github+json`
     - `Content-Type: application/json`
   - **Payload**: `{"ref":"main"}`
   - **时区**: 每个 Job 设置 **Timezone = `Asia/Shanghai`**（不设则需把下述小时数减 8 转 UTC）

3. 创建 3 个 Job（覆盖全天，总次数 ≈49/日，与原来 30 分钟全天持平，不超私仓 Actions 配额）：

| Job | Title | Schedule（间隔 + 小时） | 覆盖时段（北京） | 每日次数 |
|---|---|---|---|---|
| 1 | `美股盘中15min` | 每 15 分钟，仅小时 **21,22,23,0,1,2,3** | 美股盘中 21:00–04:00 | 28 |
| 2 | `A股盘中30min` | 每 30 分钟，仅小时 **9,10,11,13,14** | A股 09:00–15:00 | 10 |
| 3 | `低活跃60min` | 每 60 分钟，仅小时 **4,5,6,7,8,15,16,17,18,19,20** | 其余时段 | 11 |

> 说明：
> - Job 1 覆盖 21:00 起（略早于 21:30 开盘，留出盘前消息）；若想更省配额可去掉小时 `3`（少 4 次/日）。
> - Job 2 的 30 分钟档避开午休（11:30–13:00）与收盘后；若 A股也要 15 分钟：把 Job 2 改"每 15 分钟"，总次数升至约 59/日，**配额需盯紧**（或同步砍掉 Job 3 的低活跃段）。
> - 分时段后 LLM 判定次数随运行次数变化，美股盘中时段 LLM 成本约为原来 2 倍，其余时段更低。

4. 保存后逐个点 **Run job** 测试一次，确认 GitHub Actions 收到触发。

> 为什么不用 GitHub 自带 cron？GitHub schedule 有排队延迟（可能晚几分钟），
> cron-job.org 延迟 <1 分钟，基本准点触发。

### 7. 本地 .ENV 同步（可选，本地调试用）
在 `.ENV` 末尾填入同样的 `PUSHPLUS_TOKEN` / `GIST_TOKEN` / `GIST_ID`（已预留空位）。

完成后，cron-job.org 按分时段准点触发推送。
可手动触发验证：仓库 → Actions → 实时重大资讯推送 → Run workflow。

## 验证方式

```bash
# 本地诊断：多源抓取+筛选，打印将推送的内容预览，不推送、不写状态
python scripts/real_time_push.py --dry-run

# 本地单次执行（需 .ENV 已配 PUSHPLUS_TOKEN 或 WECOM_WEBHOOK）
python scripts/real_time_push.py

# 本地常驻守护进程（电脑开机期间分钟级推送）
start-realtime.bat          # 或 python scripts/real_time_push.py --loop
```

> ⚠️ 本地 --loop 与云端定时任务不要同时运行：两者共享同一 Gist 状态，
> 虽已有读-改-写合并保护，但双端同跑仍浪费 LLM 额度且可能偶发重复推送。

## 阈值调优

> ⚠️ **2026-08-04 用户口径（硬门槛，优先级最高）**：**仅强利好/强利空（`bullish`/`bearish`）才推送**。
> 弱档（mildly_bullish/mildly_bearish）、中性（neutral）、混合（mixed）一律不推，
> 覆盖全市场/板块/个股、外围科技必推、科技防漏推等全部路径。

| RT_PUSH_MODE | 推送标准 | 预计每日条数 |
|---|---|---|
| `strict`（默认，财联社风格） | **强档门槛**（仅 bullish/bearish）之上：① 全市场级 ② 板块级 ③ **龙头个股** ④ **外围科技消息**（美股/海外影响科技板块）；**非龙头个股不推** | 5-15 条 |
| `standard` | 强档门槛 + 影响分≥6 或 板块/个股级强利好利空 | 10-25 条 |
| `loose` | 强档门槛 + 影响分≥5 | 20-40 条 |

> 龙头个股 = LLM 判定的行业第一梯队公司（寒武纪、宁德时代、茅台、中际旭创等），
> 或 `watchlist.json` 的 `stocks` 中你自定义的名单（两者取并集）。
> 外围科技消息 = 富途/华尔街见闻源 + 涉及半导体/AI/算力/纳指等科技板块（同样受强档门槛约束）。

推送时段由 `RT_ALWAYS_ON` 控制：`1`=全天 7x24（含周末、隔夜海外消息），
`0`=仅 A 股交易日。改动后重新触发一轮 workflow 即生效。

## 重要限制与注意

1. **私有仓库免费额度**：GitHub Actions 私有仓库每月 2000 分钟。本工作流每次约
   1.5-2 分钟，每 30 分钟一次约 1400-1900 分钟/月，接近上限。若用量吃紧，
   在 cron-job.org 把 Schedule 改为 `0 * * * *`（每小时一次，约 700-960 分钟/月）。
   公开仓库无此限制。**建议在仓库 Actions 页面留意分钟用量**。
2. **实时性粒度**：cron-job.org 每 30 分钟准时触发（延迟 <1 分钟），做不到财联社的
   秒级。若需分钟级实时，后续可把同一脚本部署到云服务器/云函数常驻。
3. **CI 下必须配置 GIST**：没有 Gist 时状态无法持久化，脚本会**主动报错退出**，
   避免"每轮重复推送已推消息"。
4. **全部走 LLM 判定（2026-08-03 起，无规则降级直推）**：预筛通过的全部候选必须由
   LLM 判定推/不推，Python 规则不得直接通关。LLM 未回显/批次异常/无法解析的条目一律
   **不推、不落指纹**，挂起留待下一轮重新送 LLM 判定（方向与范围以 LLM 为准，避免
   规则对全文关键词扫描导致的"利空显示利好"误判）。
5. **仅强档推送（2026-08-04 起）**：direction 非 `bullish`/`bearish`（弱档/中性/混合）
   的条目不推、落指纹不重试。
6. **推送失败自动重试**：单条推送失败不记指纹，下轮自动重推。
7. **同事件只推一次**：多源报道同一事件（标题措辞不同）按事件签名合并（含开收盘/午评
   类快讯、盘中指数行情动态），同轮只推最优一条，且 48h 内已推过的同事件不再推
   （2026-08-01 三源三推、2026-08-03 美股开盘、2026-08-04 纳指盘中三推实证修复）。
