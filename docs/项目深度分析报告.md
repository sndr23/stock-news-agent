## 一、项目定位与演进脉络

**核心目标**：像财联社公众号一样，**有重大消息立刻推送到微信，日常流水静默丢弃**——即"重大资讯不漏推、日常不打扰"。

**架构演进**（依据 git 历史与代码注释）：

| 阶段 | 时间 | 形态 | 状态 |
|---|---|---|---|
| 早期 | 07-28 之前 | LangGraph 批处理管线，每日 4 次汇总推送报告（含 Web UI） | 已移除 Web UI |
| 中期 | 07-31 | 移除每日定时汇总，转向实时事件驱动推送 | — |
| 当前 | 08-02 起 | 唯一生产入口 `scripts/real_time_push.py`；批处理管线整体标记 `DEPRECATED` | 运行中 |

**当前事实**：
- 批处理管线 `src/agent/graph.py`、`src/agent/nodes.py`（`fetch_news_node`/`prefilter_node`/`llm_filter_node`/`rank_news_node`）、`calculators.py` 中的 `rank_news` 等**已无任何生产调用方**，仅作为"共享分析库"名义保留。
- 生产脚本实际只复用 `nodes.py` 的 `_call_llm_api` 与 `_repair_json` 两个函数。

                                     ▼
  ⑦ 阈值过滤（strict / standard / loose 三档）

                                     ▼
  状态持久化：GitHub Gist（云端）/ logs/real_time_state.json（本地）
  读-改-写合并防并发覆盖；48h 滚动清理；推送失败不记指纹→下轮重试

## 四、关键技术决策与工程亮点

1. **多源并行 + 失败隔离**：`ThreadPoolExecutor` 每源独立超时（`per_source_timeout=30`，`total_timeout=120`），单源挂起不影响其它源，整体最坏耗时可控。
2. **双层去重体系**：
   - 指纹层（`_news_fingerprint`）：解决"完全相同一条"的跨轮去重，按事件签名/高信号词/归一化标题分级生成。
   - 推送级事件签名（`_push_event_sig` + `_is_same_event`）：解决"同一事件的不同报道"（标题措辞/金额表述/信号词子集差异），综合 LCS 连续子串、LCS 子序列、Jaccard、方向对立守卫。**实证修复"恩智浦收购 Ambarella 三源三推"问题**。
3. **Gist 状态读-改-写合并**：本地 `--loop` 与云端并发共享 Gist 时，避免互相覆盖 `pushed` 标记（2026-08-01 实证）。
4. **LLM 判定按 idx 精确对齐**：要求 LLM 回显 `idx` 而非靠标题匹配——批处理管线实证 60 条仅 26 条标题精确命中，未对齐是被漏推的主要根因。
5. **LLM 降级策略**：批次失败/漏回显 → 规则判定（高信号词 + 预筛 ≥ 0.7 直推），**"宁可多推不可漏推重大消息"**。
6. **三级阈值 + 科技保护**：`strict`（默认，财联社风格）全市场必推、板块级强档或 ≥6、龙头个股强档或 ≥6、非龙头个股不推；外围科技（富途/华尔街 + 半导体/AI/算力）必推；科技板块级/科技龙头即使 LLM 判不推也放行（防漏推科技），但中小市值个股自身业绩/回购等仍按 LLM 否决。
7. **成本与鲁棒性细节**：
   - 候选上限 40/轮、免费模型（deepseek-v4-flash:free）、依赖 `~=` 上限约束防 breaking change（08-02 新增）。
   - 推送失败不记指纹→下轮重试，避免重大消息丢失。
   - 红涨绿跌惯例 + 中文 emoji 表达方向（企业微信 markdown 不支持内联 HTML）。
   - 依赖版本上限约束（langgraph/langchain/akshare/pydantic 等 `~=`），防依赖漂移击穿 CI。
8. **测试覆盖**：19 个测试文件 ~2850 行，历史 117 测试全过；`test_realtime_push.py`（31KB）覆盖指纹、合并、阈值、状态合并、降级等关键路径。

## 五、技术债与风险（实测/代码实证）

| # | 等级 | 问题 | 影响 |
|---|---|---|---|
| 1 | **P0** | **死代码占比 ~56%**：`nodes.py`(1901) + `calculators.py` 批处理部分 + `graph.py` 退出生产，但 `calculators` 实际被生产调用的函数仅 `calculate_prefilter_importance`/`_EVENT_KEYWORD_GROUPS`/`_extract_core_numbers`/`predict_direction_by_rules` 4 个 | 维护成本高、新人理解负担重、误改风险 |
| 2 | **P0** | **生产耦合废弃代码**：`real_time` 复用 `nodes._call_llm_api/_repair_json`，导致 `langgraph` 经 `state.py` 间接被强制依赖，无法从生产剥离 | 依赖冗余、镜像体积、潜在接口漂移 |
| 3 | **P1** | **CI 不跑测试**：`realtime-push.yml` 为省 Actions 分钟省略 `pytest`；依赖 `~=` 升级时 CI 不验证 | 生产回归不可见 |
| 4 | **P1** | **`watchlist.json` 为空**（`{"stocks":[],"sectors":[]}`）：龙头自选名单功能看似启用，实际 leader 判定完全依赖 LLM `is_leader_stock` | 功能名存实亡，用户自定义龙头不生效 |
| 5 | **P1** | **候选溢出静默丢弃**：`MAX_CANDIDATES=40` 超量候选不记指纹，下轮重复抓取/判（无害但浪费 LLM 配额） | 突发行情下重复消耗 |
| 6 | **P2** | **全局 socket 副作用**：`data_fetchers.py:181` 仍 `socket.setdefaulttimeout(AKSHARE_TIMEOUT)`（历史已从 nodes 移除，此处残留） | 影响进程内其他 socket 操作语义 |
| 7 | **P2** | **注释/代码不一致**：`_llm_judge` 注释称"不再走 `_fallback_decision` 规则直推"，但代码仍调用它作为 LLM 降级 | 属注释漂移，行为本身安全 |
| 8 | **P2** | **私有仓库额度风险**：`RT_ALWAYS_ON=1` + 30min cadence + `cancel-in-progress:false`，私有仓库 2000 min/月上限逼近（1440–1900/月），排队叠加消耗 | 月末可能超额中断推送 |
| 9 | **P2** | **实时性粒度有限**：cron-job.org 30min 粒度，非财联社秒级；每轮全量拉取各源当日数据再过滤，抓取量随轮次线性增长（指纹只缓解重复推送，不缓解抓取量） | 大行情时段延迟 + API 限流风险 |
| 10 | **P2** | **数据源稳定性**：财联社/华尔街见闻直连 API（非 akshare），版本号硬编码（`CLS_API_SV` 可环境变量覆盖） | API 变更需人工跟进 |

## 七、改进建议（按优先级）

**P0 —— 架构瘦身与解耦**
1. 将 `_call_llm_api` / `_repair_json` 抽到独立模块（如 `src/llm_client.py`），使 `real_time` 与废弃 `nodes.py` 解耦；随后可从生产依赖移除 `langgraph`，并评估归档整个批处理管线（保留 calculators 中被复用的 4 个函数 + dedup 工具）。
2. 在 CI 增加**轻量测试门禁**：仅跑 `@pytest.mark.unit`（不跑 `@integration`/网络），防止生产回归；至少对 `real_time_push` 关键纯函数做 import/lint 检查。

**P1 —— 正确性收紧**
3. 为 `watchlist.json` 填充默认龙头名单，或在 README 明示"留空则完全依赖 LLM"，避免功能名存实亡。
4. 候选溢出时也写入指纹（`pushed=False`），避免下轮重复抓取消耗。
5. 移除 `data_fetchers.py:181` 的全局 `socket.setdefaulttimeout`，改为 `requests` 显式 timeout（已有），消除全局副作用。
6. 清理 `_llm_judge` 注释与代码不一致。

**P2 —— 运维与成本**
7. 监控私有仓库 Actions 分钟用量；用量吃紧时 cadence 改为每小时或改为公开仓库。
8. 评估"每轮全量抓取"改为按各源最新时间戳增量拉取，降低 akshare/直连 API 调用量与限流风险。
9. 关注 OpenRouter 免费模型（deepseek-v4-flash:free）的质量/稳定性波动对判定准确率的影响，必要时预留可切换模型。

## 八、结论

该项目工程成熟度较高，围绕"重大资讯不漏推、日常不打扰"的核心目标，在**多源去重、LLM 判定对齐、降级兜底、并发状态一致、成本控制**等方面有大量实证驱动的精巧设计，日志与测试也较为完备。

**最突出的薄弱环节是历史代码清理与 CI 测试覆盖**：约 56% 的源码为已废弃的批处理管线，与当前实时架构脱节，且生产脚本仍间接依赖其中两个函数，导致 `langgraph` 无法剥离。**建议优先推进"架构瘦身 + 测试门禁"两项 P0 工作**，以显著降低长期维护风险，使项目回归"小而精"的稳态。
