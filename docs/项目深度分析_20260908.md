## 一、结论先行

1. **系统本质没变，但证据链的断裂点换了位置**。这仍是"事件驱动资讯推送 + 创业板单资产择时"两套系统；择时侧的方法论纪律（无前视、OOS、验门、影子期）是全项目最强的资产。与 2026-08-22/28 两轮分析相比，**代码与工程防线继续变强（LLM 三级降级链、Gist 体积守卫、快照严格门禁），而三个新的结构性问题出现在"调度层"与"数据保留层"——不在代码里，而在代码与 GitHub 平台的契约失效**（详见第五节高危项 1-3）。
2. **8 月底以来最重要的工程进展**：LLM 判定三级降级链（主失败→3 个免费备选，2026-09-07）；推送治理 P0-P1b 五批次（事件级去重/失败挂起重试/日限额/公告白名单/watchlist 直通/Gist 950KB 体积守卫）；盘中快照从"口径声明"落地为"可审计归档 + 严格回放回测"（2026-09-02/03）；策略健康度熔断与执行滑点埋点（2026-08-29）。
3. **策略结论维持原判且更明确**：严格口径下择时策略（+145.6%，回撤 -40.3%）仍跑输买入持有（+152.7%，回撤 -69.7%）——系统的价值是"用约 38% 平均仓位拿到接近满仓的收益、回撤砍掉近 30pp"，是**回撤管理工具，不是 alpha 机器**。修正层 ±0.30 不可回测仍是回测与实盘行为差异的最大单点（实测仅资讯 ±0.06 就能翻转 15.7% 的档位决策）。
4. **资讯信号有效性验证链存在结构性断裂（本次审查最重要发现）**：`pushed_events` 只保留 48h 滚动窗口（real_time_push.py:154/1884），而 `signal_backtest` 名义回测 60 天窗口、统计后 1/3/5/10 日一致率（signal_backtest.py:57-59）——**后 3/5/10 日维度在当前数据机制下永远无法产出**（事件在 horizon 成熟前已被滚出状态），后 1 日的 65% 一致率也建立在 48h 样本、利空单边（利空 14/14 vs 利多 1/9）之上。"可信度基石"目前只能产出 1/4 个维度的低证据力数字。
5. **两个生产功能实际处于"静默失效"状态**：盘前简报自 2026-09-01 起因 GitHub schedule 延迟 4.5h+ 全部误判为盘后复盘（用户每天收到两份复盘、没有盘前简报，但没有任何报错）；推送源健康告警的 streak 存本地文件，云端 Actions 每轮新 runner 不持久，"连续 6 轮空推送告警"在云端**永远无法触发**。
6. **安全面有一个需要立即处理的项**：公开仓库已入库的审查文档（fc9ee7c）泄露了**现役** GIST_TOKEN 的前 8 位特征（与 .ENV 在用 token 为同一个），建议直接轮换；git 历史中仍残留一个已被 GitHub 自动吊销的 fine-grained PAT 明文（5f66540）。

## 五、风险清单（按严重度，含证据定位）

### 🔴 高危

1. **资讯信号回测的"数据保留期 × 评估 horizon"结构性矛盾**——pushed_events 48h 滚动窗口 + 300 条上限（real_time_push.py:154, 1884-1888）vs 回测默认 60 天窗口/后 10 日 horizon（signal_backtest.py:57-59）。后果：后 3/5/10 日一致率永远"无数据"，周六运行的"样本最全"设计意图（signal-backtest.yml:8 注释）落空；后 1 日的 65% 一致率样本全部来自最近 48h，且利空 14/14 vs 利多 1/9 的单边结构本质是下跌市 beta 巧合，却被系统提示"信号具备跟踪价值"（signal_backtest.py:565-566 阈值无 regime 免责）。**回测可信度基石的证据链断裂**——需要为回测建立长周期事件留存（如独立回测事件档案文件或拉长该表保留期）。
2. **盘前简报自 09-01 起静默失效**——market-brief.yml:73 用**执行时刻** UTC 时间 <02:00 判 morning，而 GitHub schedule 实测延迟 4.5h+（Actions API：09-02~09-08 早间 cron 全部 13:0x BJT 执行），恒大于判定线 → **全部落入 evening 分支**。用户每天收到两份盘后复盘、没有盘前简报，无任何报错。修复方向：判定应基于 `github.event.schedule`（cron 表达式）而非 wall-clock。
3. **GitHub schedule 延迟失控（4.5~6.3h）**——market-brief/citic-pos 依赖自带 cron 的"分钟级延迟可接受"假设已失效（yml:8-9 注释自证）；citic 17:00 日报实际 21:00~22:35 执行，"当日盘后"语义破坏，其 4×10min 重试机制的设计前提（17:00 后数据陆续公布）也已错位。chinext-timing 用外部 cron-job.org 精点触发（14:45:20 BJT 实测）是正确路线的实证——依赖 GitHub schedule 的 3 个 workflow 均应评估迁移。
4. **源健康告警（P1b）在云端结构性失效**——streak 计数落本地文件 logs/source_health.json（data_fetchers.py:1287-1309），GitHub Actions 每轮新 runner 文件不持久 →"单源连续 6 轮空推送"告警在生产环境**永远无法触发**（本地 logs 实测：财联社 streak=6 的告警来自本地运行，云端从未累计）。该 P1 功能只对本地 --loop 生效，需并入 Gist 状态才能生效。

### 🟠 中高

5. **择时策略"回测 vs 实盘"行为差**——生产实盘 = 核心层 + 不可回测修正层（±0.30，实测资讯 ±0.06 翻转 15.7% 档位）+ 实时硬风控通道 + 14:45 快照执行摩擦；回测数字只覆盖核心层日线代理（run_chinext_timing.py:1150-1151 自认近似）。修正层 IC 验门样本不足（影子 history 有效样本 <10），"回测验证过"的表述只覆盖一半决策路径。缓解：快照归档已开始积累（09-02/03 起），真实回放基线形成前不得混用两类数字（README:68 已成文）。
6. **SNA-06 集成悬空**——intraday_sweep.py + 31 用例未入库、接线已拆、死代码残留，task-board/status 文档三处不同步；历史上已因同一断层引发 Actions 崩溃（9f908f8）。需提交文件+恢复接线+文档同步三步收口。

## 六、改进建议（按优先级）

**P0 —— 修复"静默失效"三件套（全部有明确修复方向，工作量小）**

1. **修盘前简报误判**：market-brief.yml 的类型判定改用 `github.event.schedule`（cron 表达式本身区分早晚），或在脚本内用"当前北京时间 <11:00 → morning"的区间判定；同时评估三个依赖 GitHub schedule 的 workflow 迁移到 cron-job.org（chinext-timing 的精点实证已是模板）。
2. **打通回测数据留存**：为 signal_backtest 建立长周期事件档案——最小改动是 pushed_events 在滚动清理前把成熟事件（含 dir/stocks/scope/t）追加写入独立的 `backtest_events.json`（或 Gist 新文件，注意 1MB 容量），回测读档案而非 48h 状态窗口；这使后 3/5/10 日维度真正可评估，是"可信度基石"从蓝图变现实的前提。
3. **修源健康告警云端失效**：source_health streak 并入 Gist 状态（factor_state 已有同型结构 source_health 字段可复用模式），云端跨轮累计；顺带处理 `_zero_push_streak` 模块级计数同样不跨轮的问题。
4. **轮换 GIST_TOKEN**：旧 token 特征已入公开 git 历史（fc9ee7c）；GitHub 轮换新 PAT → 更新 Actions secrets + 本地 .ENV → 删除旧 token。顺带可选：git filter-repo 清 5f66540 历史（已有自动吊销兜底，非必须）。

**P1 —— 收口集成断层与容量**

5. **SNA-06 三步收口**：提交 intraday_sweep.py + test_intraday_sweep.py → 恢复 run_once 接线（9f908f8 摘除点的反向补丁，含 `_load_watchlist_stocks` 死代码复活）→ 同步 task-board/status.md。历史教训（Actions import 崩溃）要求"提交文件"与"恢复接线"必须在同一 commit。
6. **Gist 容量治理**：real_time_state 拆分（seen 单独文件或裁剪周期缩短）或压缩守卫策略与 `_prune_seen` 口径统一（压缩也按"已推优先淘汰"），消除 917KB→1MB 之间的压缩瞬变窗口。
7. **建立最小独立 CI**：加一个 `on: push` 的纯测试 workflow（延续 -m unit 门禁，5 分钟级）；加 .gitattributes（`*.py text eol=lf`）根治 CRLF 假脏——这两个是成本最低的工程健康改善。
8. **修正层验门样本积累**：影子 history 有效样本已近 10 条门槛（09-04 预计达标后 _exp_modifier_ic 可出首批结论），按既定纪律推进——修正层是"回测实盘行为差"的核心，其验门结论直接决定 v5.1 之后的方向。

**P2 —— 长期**
